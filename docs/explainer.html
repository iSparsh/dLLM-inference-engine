dLLM Engine Field Guide

We are building a faster engine for a diffusion language model on a laptop GPU, then testing whether it beats the best normal-LLM engine on speed and what it costs in accuracy. This page shows how the pieces work and how the work fits together. The words-only version is GUIDE.md; the exact numbers are in PLAN.md.

τ (tau) is the confidence threshold: a guess is kept only if the model is at least this sure of it. Sections 4 and 5 explain each item in detail.

1 · THE BOTTLENECK

A laptop GPU spends its time reading weights, not doing math

Every forward pass of the model reads all 3.09 GB of weights from GPU memory. At 256 GB/s that takes about 12 ms, however little arithmetic the pass needs. A normal (autoregressive) model gets one token out of each read. A diffusion model processes a whole 32-token block in the same read and keeps every guess it is confident about.

2 · HOW A BLOCK GETS WRITTEN

Step through one 32-token block

A block starts with its first token known and 31 blanks (MASK). Each pass predicts every blank in the block. Blanks in the current group of 8 whose confidence clears τ are committed, and the most confident one is always committed so every pass makes progress. When all 32 are filled, a final commit pass saves the block into the KV cache and produces the first token of the next block.

3 · WHERE THE TIME GOES

About 4 of the reference's 17.6 ms per pass are avoidable

NVIDIA's code for this model takes 17.6 ms per pass on the laptop in its performance power mode. About 13.8 ms is the matrix multiplies, already at the cuBLAS floor. The rest is roughly 1,400 small kernels with idle gaps between them, plus copying the KV cache before every attention step. That overhead is what our engine removes, and the cache copying grows with the length of the text.

4 · WHAT WE BUILD

Reuse the model and cuBLAS. Write the parts only a dLLM needs.

We don't reimplement the model. Hugging Face loads the weights and the tokenizer, and cuBLAS does every matrix multiply, since it is already at the memory limit for our shapes. We write the driver: the program that runs the block-by-block loop, owns the KV cache and records each pass as a CUDA Graph. We also write three groups of CUDA kernels that replace the slow PyTorch operations around the matrix multiplies.

5 · SPENDING THE FREE CAPACITY

Fewer passes per answer, not just faster passes

A 64-row pass costs about the same as a 32-row pass on this GPU, and the standard recipe never uses that. These four ideas do. For P2 and P3 we first measure, from recorded traces of real runs, how often the guesses they depend on would be right. That measurement goes in the report whether or not we build the feature.

IdeaWhat changesOutput unchanged?Build it if
P1 stop on timeStop at the first committed end-of-text and skip the last commit passyesalways (easy, 3–6% of passes)
P2 merge the commit passRun "commit block k" and "first pass of block k+1" as one 64-row pass, using a guessed first token, checked afterwardsyes, after the checkthe guess is right ≥ ~70% of the time
P3 two steps per passRun this step and a guessed next step together; keep the second half if the guess was rightyes, after the checkguesses right ≳ 40% of the time (~1.2–1.45× fewer passes)
P4 smarter commit rulesFor example, commit a position whose guess held for two passesno, re-check accuracytime allows
6 · HOW WE WILL KNOW IT WORKED

Fast engine + dLLM against fast engine + AR

The headline compares our dLLM engine with llama.cpp, the best engine there is for normal models. Our own engine also runs the normal model (as block size 1). If that lands near llama.cpp, it shows our engine is genuinely fast, so any dLLM advantage comes from the decoding method. Accuracy comes from 100 GSM8K math problems, the same 100 for every setting.

9 · WORDS YOU WILL SEE

Glossary

Token
A piece of text, roughly a word. The vocabulary has 151,936.
Weights
The model's fixed numbers: ~1.5 B of them, 3.09 GB. Read in full every pass.
Forward pass
One run of the model over its input. Our unit of cost; ~12 ms minimum on the laptop.
Logits
The model's score for every vocabulary token at each position.
AR (autoregressive)
One token per pass. How normal LLMs work.
dLLM (block diffusion)
Fills a 32-token block of blanks over several passes, several tokens per pass.
Threshold τ
Confidence a guess needs to be kept. Higher is slower and more accurate.
Commit
Keep a guessed token for good. The commit pass saves a finished block into the cache.
KV cache
Saved K and V vectors for every past token and layer, so they aren't recomputed.
Block-causal attention
A position sees its own block in both directions and earlier blocks only.
Grouped-query attention
12 query heads share 2 K/V heads, 6 each.
Memory-bound
Time is set by bytes read, not arithmetic. True for us at batch size 1.
Kernel
One function launched on the GPU. The reference launches ~1,400 per pass.
CUDA Graph
A recording of many kernel launches, replayed with one launch.
Driver
Our program that runs the decode loop, owns the cache and replays the graph.
cuBLAS
NVIDIA's matrix-multiply library. We use it rather than compete with it.
Ablation waterfall
Time per pass after adding each optimization in turn.
GSM8K
Grade-school math word problems with one numeric answer. Our accuracy test.
llama.cpp
The best existing engine for normal LLMs on consumer hardware. Our AR baseline.
